# Gate A · six runs at scale

**Date:** 2026-08-14
**Corpus:** [`corpus/gate-a.json`](../corpus/gate-a.json), 30 repositories, pinned
**Binary:** built with Go 1.25, so the compiled-in type checker accepts the whole corpus

```sh
lectio backtest --corpus corpus/gate-a.json --ablate --cases 5                      # 2
lectio backtest --corpus corpus/gate-a.json --ablate --cases 5 --collapse max       # 1
lectio backtest --corpus corpus/gate-a.json --ablate --cases 5 --target corrected   # 3
lectio backtest --coupling */                                                       # 4
lectio backtest --corpus corpus/gate-a.json --ablate --cases 5 --target symbols     # 5
lectio backtest --corpus corpus/gate-a.json --ablate --cases 5 \
    --target corrected-symbols                                                      # 6
```

## Verdict: FAIL, and the failure is real

The first run at scale produced a FAIL that could be read two ways: the ranking
is not good enough, or the metric rewards size and a size baseline wins by
construction. Both fit the number. Three runs later the fork is closed.

| Run | Change | lectio | largest files | Gap |
| --- | --- | --- | --- | --- |
| 1 | the original, `--collapse max` | 43.2% | 48.1% | −4.9 |
| 2 | harness size bias removed | 41.9% | 48.1% | −6.2 |
| 3 | the spec's tiebreaker target | 28.5% | 35.5% | −7.0 |

Removing the bias made lectio *worse*. Controlling for size did not exonerate
it. Changing the target variable made it worse again. The metric was not the
problem.

A fourth run tested the differentiator directly rather than through
precision@10, on a far larger sample than the gate uses: **lift 1.02 across
2,311 newcomer corrective commits.** Hidden coupling has no relationship to
where newcomers go wrong.

Runs 5 and 6 removed the file-path prior entirely by grading declarations
instead of files — the one remaining explanation under which the ranking could
be better than it measured. Lectio beats all four baselines there and is beaten
about two to one by a control that simply ranks the longest declarations:

| Run | Target | lectio | best baseline | largest symbols |
| --- | --- | --- | --- | --- |
| 5 | symbols | 10.5% | 8.3% | **22.8%** |
| 6 | corrected symbols | 7.7% | 1.9% | **17.1%** |

Size did not come from grading file paths. It followed the measure down to
symbols and won there too.

## Run 1 · the first result was partly the harness's fault

The backtest ranks symbols and scores files, and the rule bridging the two was
max — applied implicitly, by walking the score-sorted symbol list and taking
each file at its first appearance. That reads as neutral and is not: a file
with sixty symbols gets sixty chances to place high, a file with three gets
three.

Measured across five corpus repositories, it put lectio's top ten files at 3.5×
the repository's median symbol count, overlapping the largest-files baseline
6/10. The harness was scoring a partial reimplementation of the baseline lectio
lost to.

The rule is now explicit, defaults to mean, and is reported with every result.
Re-running with `--collapse max` reproduces 43.2% to the decimal, so the
original number was sound — it was measuring something slightly different from
what it claimed.

**The fix cost lectio 1.3 points.** That direction is the finding. If max had
been inflating the *baseline*, removing it would have helped; instead it was
inflating lectio, which had been quietly borrowing the winning strategy.

## Run 2 · size-controlled, and the ranking still adds nothing

```
  strategy                      prec@10     recall        MRR   median
  --------------------------------------------------------------------
  lectio                          41.9%      41.2%      0.702    40.0%
  largest files                   48.1%      45.7%      0.751    50.0%
  size-proportional draw          44.1%      42.8%      0.637    50.0%
  most churned, 12mo              41.5%      36.1%      0.704    40.0%
  most distinct authors           41.1%      35.8%      0.669    40.0%
  most recently modified          40.2%      35.8%      0.564    40.0%
```

**A random draw weighted by file size scores 44.1%** — above the seven-signal
ranking. It is a control rather than a baseline and does not decide the gate,
but it is the single most informative row in the table. Whatever the ranking is
computing, a coin flip biased by file length does it better.

The stratified table splits the same cases by candidate file size:

```
  strategy                   Q1 smallest          Q2          Q3  Q4 largest
  --------------------------------------------------------------------------
  lectio                           24.5%       27.3%       33.6%       51.7%
  largest files                    30.0%       27.5%       33.9%       53.1%
  most churned, 12mo               20.3%       20.9%       32.3%       50.1%
  most distinct authors            18.9%       18.9%       32.6%       49.9%
  most recently modified           20.0%       19.5%       31.3%       50.1%
  --------------------------------------------------------------------------
  size spread within band            23x          2x          2x          7x
```

Lectio wins no band. The Simpson's-paradox pattern — behind overall, ahead
everywhere — would have shown the metric rewarding size, and it is absent. The
reading rules were committed before the run; this is the branch they landed on,
not one chosen afterwards.

**The spread row is why the conclusion is narrower than "the ranking is bad".**
Quartiles by file count do not equalize size within a band: Q1 spans 23× and Q4
spans 7×, so a size strategy still holds real size information inside them, and
winning there is weak evidence about choices. Only Q2 and Q3 are tight, at 2×
each — and there the gap is **0.2 and 0.3 points**.

So where size is genuinely held constant, lectio and largest-files are the same
strategy. The ranking is not making worse choices. It is making the same ones,
for a great deal more computation.

## Run 3 · the tiebreaker fails too, and by more

The spec anticipated this and named a way out:

> weight toward files where a newcomer's early commits got reverted or fixed

That is a different target variable rather than a different weighting: score
against where newcomers *went wrong*, not where they went. It is also the
target hidden coupling should be strongest on, since touched-files is precisely
the measure a coupling signal should be weakest on.

```
Gate A · 40 cases scored, 74 discarded
  65 had too little ground truth on the corrected target to score

  strategy                      prec@10     recall        MRR   median
  --------------------------------------------------------------------
  lectio                          28.5%      35.2%      0.640    30.0%
  largest files                   35.5%      45.9%      0.681    35.0%
  size-proportional draw          32.7%      43.3%      0.538    30.0%
  most churned, 12mo              31.5%      35.7%      0.623    30.0%
  most distinct authors           29.8%      34.3%      0.615    29.3%
  most recently modified          28.2%      34.1%      0.514    29.3%
```

Lectio now loses to **three** baselines instead of one, and largest-files leads
every size band including the tight ones — Q3 by 11 points. The size-weighted
coin flip beats it here too.

Two caveats, neither of which rescues the result. Only 49 of 114 cases carry
two or more corrected files, so this runs on 40 cases after degraded revisions
are discarded; and `MinCorrectedFiles` is deliberately 2 rather than 3, because
requiring more would select the contributors who broke the most things — a
different population, not a smaller sample. The direction is consistent enough
across bands that sample size is not what is producing it.

## What each signal is worth

| Signal | touched (run 2) | corrected (run 3) |
| --- | --- | --- |
| Centrality | **+3.8 pp** | −0.5 pp |
| Churn | +2.4 pp | +1.5 pp |
| Hidden coupling | −0.8 pp | −0.5 pp |
| Fix density | −0.1 pp | 0.0 pp |
| Orphaning | +0.5 pp | +0.8 pp |
| AI density | 0.0 pp | 0.0 pp |

Read the columns together and only one signal survives both: churn — the
cheapest of the seven, and the one the spec warns against becoming a proxy for.

Centrality was the ranking's best signal on touched-files and turns slightly
negative on corrected-files. That is coherent rather than contradictory: highly
central code is well-trodden and well-tested, so a newcomer is *less* likely to
break it. It is also the opposite of what the reading path is built to assume.

**Hidden coupling is negative on both targets.** The deltas are too small to
claim it is harmful, but it was given the target it should perform best on and
did not. Run 4 tests it directly.

AI density measured exactly zero because no repository in the corpus records
machine authorship. That is the signal behaving as designed, not a null result.

## Run 4 · the differentiator, measured directly

Precision@10 is the wrong instrument for hidden coupling. A signal firing on
seventy file pairs across a repository can be entirely correct and still move a
top-ten list by a fraction of a point, so a −0.8 pp ablation delta is weak
evidence either way. `CheckCoupling` asks the claim as the spec states it:

> if touching A and forgetting B is what breaks newcomers, and the signal finds
> those pairs first, that is what makes the tool feel clairvoyant

Stated as something falsifiable: a newcomer's corrective commits should land on
hidden-coupled files more often than that same newcomer's ordinary commits do.
Lift is those two rates divided. 1.0 is no relationship.

This machinery had existed since the backtest package was written and was never
reachable from the command line, so the product's central claim had never been
measured. It is now `lectio backtest --coupling`.

```
  repository                 pairs   fixes on coupled base rate    lift
  ----------------------------------------------------------------------
  hashicorp__hcl                16      87         7        4%    1.90
  spf13__afero                   6      43        16       28%    1.31
  charmbracelet__bubbletea     189      99        59       46%    1.30
  charmbracelet__lipgloss       54      52        43       68%    1.21
  ...
  go-git__go-git               235     275       127       52%    0.89
  uber-go__zap                  53      46        17       47%    0.78
  julienschmidt__httprouter      1      15         5       64%    0.52
  ----------------------------------------------------------------------
  pooled                      1554    2311      1515       64%    1.02
```

**Lift 1.02, over 2,311 newcomer corrective commits and 1,554 coupled pairs
across 29 repositories.** Twenty-four repositories cleared both sample-size
guards; their lifts cluster tightly around 1.0, and the two largest excursions
sit on the thinnest evidence — hcl's 1.90 rests on a 4% base rate, where the
ratio is unstable by construction.

One limitation, in the same direction as the harness's other one: the coupling
check has no degradation guard. `relatedness` uses call edges to decide whether
a co-change is already explained by a static dependency, so a revision whose
dependencies resolve badly reports slightly more pairs than one that resolves
cleanly — go-git gave 235 pairs on one run and 233 on another. That is a 1%
effect on the numerator of a ratio that came out at 1.02, and it is worth
fixing before the check is used to argue for a *positive* result.

This is not a sample-size problem. It is the clearest result in the four runs:
**hidden coupling does not predict where newcomers go wrong.** The signal finds
real co-change pairs that no import explains — 1,554 of them — and corrective
work does not concentrate on them.

The product is staked on this signal. Centrality and churn are computable by
anyone; the spec's case for the tool existing is that co-change minus static
dependency surfaces what a senior engineer knows and cannot articulate. On this
corpus it surfaces something, and that something has no relationship to where
newcomers get into trouble.

## Runs 5 and 6 · symbol granularity, and the pass that is not one

Every measure in runs 1 through 3 scored a set of file paths, and file size is
a strong prior on any of them. That was the last explanation left standing:
maybe the ranking is fine and the *unit* was wrong. Lectio ranks symbols
natively and only collapsed to files because the harness required it, so the
collapse was throwing away the thing being measured.

Grading declarations needed three pieces: line ranges per commit, a syntax-only
parse of each changed file at the revision where the change landed, and a match
back to the symbol table **by name**. Names rather than positions, because by
the time a newcomer commits the file has moved under them — the regression test
puts `Parse` at lines 3–5 in the index and 103–105 at commit time, which any
position-based match gets wrong.

The baselines had to be restated, and **that restatement was fixed before any
symbol-level number existed**, because choosing it afterwards is how a gate gets
argued past. Each keeps its own signal and inherits it: "the biggest files"
becomes "the symbols in the biggest files, in source order" — what the
file-level baseline actually recommended — not "the biggest symbols".

```
  strategy                      prec@10     recall        MRR   median
  --------------------------------------------------------------------
  lectio                          10.5%       5.6%      0.268    10.0%
  most churned, 12mo               8.3%       4.5%      0.178     0.0%
  largest files                    6.9%       3.8%      0.163     0.0%
  most distinct authors            6.5%       3.6%      0.159     0.0%
  size-proportional draw           6.0%       4.2%      0.164     0.0%
  most recently modified           4.7%       1.9%      0.139     0.0%
  largest symbols                 22.8%      13.8%      0.467    20.0%

PASS beat all 4 baselines — but largest symbols scored higher, and it is a control
```

**Lectio passes the gate as written, and the pass means nothing.** The
largest-symbols control more than doubles it, and leads on every column: recall
13.8% against 5.6%, MRR 0.467 against 0.268, median 20% against 10%.

That control exists precisely to ask this question, and it was defined and
committed before the run. It asks whether size simply follows the measure down
from files to symbols. It does. Changing granularity did not remove the size
prior, it relocated it — and against a size heuristic expressed at the matching
granularity, the ranking loses by more than it ever lost at file level.

Banding by declaration size does not rescue it either:

```
  strategy                   Q1 smallest          Q2          Q3  Q4 largest
  --------------------------------------------------------------------------
  lectio                           11.0%        7.5%        8.3%       13.7%
  largest symbols                  10.3%       14.1%       11.9%       23.7%
  --------------------------------------------------------------------------
  size spread within band              3x          2x          3x         23x
```

Lectio takes the smallest band by 0.7 points and loses the other three by 6.6,
3.6 and 10.0. Q1 through Q3 are tight — 3×, 2×, 3× — so this is not a
composition artifact the way the file-level Q1 result was; where size is
genuinely held constant, largest-symbols is still ahead.

That result forced a change to the reading rule, which is worth stating
plainly because this document argues elsewhere that rules should be fixed in
advance. The rule counted bands and ignored margins, so it called one narrow
win against three heavy losses "mixed". It now weighs the mean per-band margin
against the ablation's existing noise floor. The change is symmetric — it makes
a narrow *lectio* win read as unsettled by exactly the same threshold, and a
test asserts that — so it is a correction to a rule that misreported rather
than a threshold moved to obtain an answer.

Run 6 repeats the pattern on corrective commits, with a wider baseline margin
and the same ceiling: lectio 7.7%, best baseline 1.9%, largest symbols 17.1%.
Thin at 31 cases — 62 of 114 have too few corrected declarations to score — so
read it as agreeing with run 5 rather than as independent evidence.

A control cannot fail the gate. The spec names four baselines and adding a
fifth after seeing the score is the goalpost move the baseline/control split
exists to prevent, so the verdict stays PASS. It is now printed in warning
colour with what undercuts it on the same line, because a PASS beside a control
that doubled it is the most misleading thing this report could print.

### What the ablation says there

| Signal | run 5 (symbols) | run 6 (corrected symbols) |
| --- | --- | --- |
| Centrality | **+2.4 pp** | −0.6 pp |
| Churn | +0.5 pp | −0.3 pp |
| Hidden coupling | −0.1 pp | +0.6 pp |
| Fix density | −1.1 pp | −1.3 pp |
| Orphaning | −0.4 pp | −0.6 pp |
| AI density | 0.0 pp | 0.0 pp |

Centrality is the only signal that is positive anywhere, and it goes negative
on corrective work — the same reversal the file-level runs showed, and for the
same reason: central code is well-trodden and well-tested, so a newcomer is
less likely to break it. On run 6 every signal is inside noise or negative.

## Corpus coverage

- 26 of 30 repositories produced at least one case; 114 attempted, 85 scored on
  the file targets, 75 on symbols and 31 on corrected symbols.
- The 4 producing none — `fatih/color`, `julienschmidt/httprouter`,
  `mitchellh/mapstructure`, `pkg/errors` — are the intended negative controls.
  Case selection declining them is correct behavior.
- 29 discards, every one the same failure: the rewound revision had no
  type-checkable Go at all, usually predating Go modules. Not partial
  degradation — the 20% threshold never came into play.
- Run 3 additionally skips 65 cases for insufficient corrective history, before
  indexing rather than after.
- Runs 5 and 6 skip cases whose commits resolve to fewer than three
  declarations — 10 and 62 respectively. Unlike the file targets this can only
  be known after indexing, since attribution needs the symbol table to match
  names against.

### The case set is not stable, and the report now says so

Runs 1 through 3 scored 85 cases each and reproduced to one decimal place.
Later repeats of the identical command scored **77**, and the discard reason
shifted: 8 revisions that had previously type-checked cleanly now failed the
degradation guard.

Nothing in the ranking moved. Which cases survive depends on whether each
rewound revision's dependencies resolve, which depends on the module cache and
on the network. `MaxDegraded` behaved correctly — those 8 cases moved from
scored to discarded rather than being scored on a broken index — but the report
gave two different populations the same identity.

| | cases | lectio | largest files | size-proportional |
| --- | --- | --- | --- | --- |
| 85-case set | 85 | 41.9% | 48.1% | 44.1% |
| 77-case set | 77 | 41.4% | 47.6% | 44.1% |

Every ordering, every gap and every conclusion is unchanged; the totals move by
about half a point. That is the size of the effect, and it is well below any
difference this document rests on.

Reports now carry a fingerprint of exactly which cases were scored. Two numbers
are comparable when it matches. The numbers quoted above are from the 85-case
set, `--collapse mean`.

## What this means

By the spec's own rule, **phase 1 has failed** — not on a technicality, and not
because of how it was measured. Six independent attempts to find a reading
where the ranking earns its place came back negative, including the one the
spec proposed as the tiebreaker and the one that removed the file-path prior
altogether.

Three findings, and the last two are the serious ones.

**The ranking adds nothing over file size.** Once size is held constant, lectio's
ordering is indistinguishable from sorting by file length — 0.2 and 0.3 points
apart in the two bands where size is genuinely controlled. It is not choosing
badly. It is not choosing differently. A random draw weighted by file size
outscores it.

**The differentiator does not differentiate.** Hidden coupling is what the spec
offers as the reason this tool should exist rather than a shell alias. Measured
directly, on twenty-eight times the sample the gate itself uses, it has no
relationship to where newcomers go wrong. That is not a tuning problem, and no
weighting fixes a signal whose lift is 1.02.

**Size is not an artifact of the unit.** Grading declarations instead of file
paths was the last standing explanation under which the ranking might be better
than it measured. It is now tested, and the answer is that size followed the
measure down: the longest declarations predict newcomer work more than twice as
well as seven signals do. The prior was never about files.

What would change the answer, in rough order of cost:

1. **A different definition of hidden coupling.** The current one is Jaccard
   co-change minus static reachability. Run 4 falsifies that specific
   definition, not the intuition behind it. Any replacement should be proposed
   before seeing which one scores best, and tested with `--coupling` rather
   than through the gate.
2. **A size-orthogonal target.** Every measure across six runs correlates with
   how much code there is — files, declarations, either way. A target that
   holds size constant by construction (did they touch this symbol *rather
   than its neighbours of the same size*) would ask a question size cannot
   answer. That is a new metric, not a new weighting, and it may not exist.
3. **A different premise.** The backtest measures what people touched, which was
   always a stand-in for what they needed to understand. Those may simply not
   be close enough, in which case Gate A is unanswerable from git history and
   the question needs users rather than a corpus. After six runs this is the
   most likely reading, and it is not a reason to proceed as though the gate
   had passed.

What should not happen: tuning weights against these numbers. Every strategy
that beat lectio beat it by being more size-correlated, so fitting to this
metric produces a tool that recommends the biggest thing available — the
failure mode the product exists to prevent. The weights are unchanged from
before all six runs.
