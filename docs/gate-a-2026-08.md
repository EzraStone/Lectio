# Gate A · first run at scale

**Date:** 2026-08-14
**Corpus:** [`corpus/gate-a.json`](../corpus/gate-a.json), 30 repositories, pinned
**Command:** `lectio backtest --corpus corpus/gate-a.json --ablate --cases 5`
**Binary:** built with Go 1.25, so the compiled-in type checker accepts the whole corpus

Run twice, independently, with identical numbers to one decimal place.

The gate requires beating **all four** baselines. Lectio beat three — churn,
recency, and distinct authors — by one to three points. It lost to *largest
files* by 4.9 points. By the spec's own rule, phase 1 has failed.

## What each signal is worth

| Signal | Δ precision@10 when removed |
| --- | --- |
| Centrality | **+5.2 pp** |
| Churn | +1.2 pp |
| Hidden coupling | −0.8 pp |
| Fix density | −0.7 pp |
| Orphaning | −0.2 pp |
| AI density | 0.0 pp |

Only centrality earns its place. Churn contributes about a point. The other
four are indistinguishable from noise at this sample size, and three of them
are nominally negative.

**The differentiator does not differentiate.** The spec stakes the product on
hidden coupling being the signal that makes someone say they would not have
thought of that. On 85 cases it moves precision@10 by −0.8 points. That is not
"hidden coupling is harmful" — the deltas are far too small for that claim —
but it is a clear absence of the effect the spec predicted.

AI density measured exactly zero because no repository in the corpus records
machine authorship. That is the signal behaving as designed, not a null result.

## The most important thing in this table is not the verdict

**"Largest files" won.** The best single predictor of what a new contributor
touched in their first ninety days is how big the file is.

That is the spec's second named failure mode, arriving exactly as described:

> The backtest measures whether the ranker predicts what people *touched*,
> which stands in for what they needed to *understand* — not the same thing. A
> newcomer might touch config constantly and understand nothing.

A newcomer touches big files because big files are where the code is. It does
not follow that reading the ten biggest files is good orientation — and if it
did, the product would not need to exist. So this run produces two readings,
and they demand different responses:

1. **The ranking is not good enough.** Take the FAIL at face value; the seven
   signals do not beat a one-line heuristic.
2. **The metric is measuring the wrong thing.** Precision against touched-files
   rewards size, so a size baseline wins by construction, and a ranking that
   deliberately avoids trivia is penalized for it.

Both readings are consistent with this data. Deciding between them is the next
piece of work, and it cannot be done by tuning weights — fitting to a metric
that rewards size would produce a tool that recommends big files, which is the
failure it is meant to prevent.

The spec anticipated needing a tiebreaker here and named one:

> weight toward files where a newcomer's early commits got reverted or fixed

That is a different target variable, not a different weighting: score against
the files where newcomers *went wrong*, rather than the files they touched.
`internal/backtest/coupling.go` already isolates newcomer fix and revert
commits for the second backtest, so the machinery exists.

## Corpus coverage

- 26 of 30 repositories produced at least one case.
- 4 produced none: `fatih/color`, `julienschmidt/httprouter`,
  `mitchellh/mapstructure`, `pkg/errors`. All small or frozen, which is why
  they were included as negative controls — case selection declining them is
  correct behavior.
- 114 cases attempted, 85 scored, **29 discarded**.

Every discard was the same failure: the rewound revision had no type-checkable
Go at all. These are rewind points early in a repository's life, often
predating Go modules, where `go/packages` can load nothing. This is a real
limit on how far back the harness can reach, and it is not partial degradation
— the guard's 20% threshold never came into play, because these revisions
produced zero usable packages rather than a thin graph.

## Caveats a reader should apply

- **Small repositories inflate every strategy.** In a repo with twenty source
  files, a top-ten list covers half of it, and precision@10 approaches the base
  rate for everything. The corpus deliberately mixes sizes, but the effect is
  not controlled for.
- **Five cases per repository, capped.** Repositories with more contributors
  are not weighted more heavily, by design — the mean is over cases, not
  pooled predictions — but 85 cases from 26 repositories is a modest sample.
- **The deltas below ±1.5 pp should not be read as effects.**
